# Правила стиля кодирования для Zig (консольный клиент Linux)

## Именование
- Все переменные — в `snake_case`.
- Все функции — в `camelCase`.
- Структуры и типы — в `PascalCase`.

## Обработка ошибок (критично для HTTP-клиента)
- Не использовать `try` в «горячих» путях (например, в цикле проигрывания треков или при частых запросах к API). Вместо этого применять явную обработку через `catch` или `if (err) |value| { ... } else |err| { ... }`.
- Для всех HTTP-запросов обязательно обрабатывать возможные ошибки сети и таймауты; не игнорировать возвращаемые ошибки.
- Если функция может вернуть ошибку, её тип должен быть явно `!T`; не скрывать это через опционалы без необходимости.
- Ошибки HTTP-клиента должны быть типизированы (свой `error`-сет), а не сводиться к общему `error.HttpError`.

## Управление памятью и аллокаторы
- Все функции, выделяющие память, должны принимать `allocator: std.mem.Allocator` как явный параметр.
- В публичных API не использовать глобальные аллокаторы; передавать аллокатор из вызывающей стороны.
- Избегать скрытых аллокаций: любые вызовы, которые могут выделять память, должны быть очевидны по сигнатуре и контексту.

## Работа с ресурсами (файлы, сокеты, соединения)
- Всегда освобождать ресурсы через `defer` рядом с местом их получения (например, `defer file.close()` сразу после открытия).
- Для сложных сценариев освобождения (несколько ресурсов, условные пути) использовать `errdefer` там, где это улучшает читаемость и надёжность.
- HTTP-соединения закрывать явно; не полагаться на сборку мусора или на то, что ОС сама приберёт сокеты.

## Документация и комментарии
- Перед каждой публичной функцией писать комментарий в формате `/// Описание назначения функции и ключевых особенностей.`
- В комментариях к функциям, взаимодействующим с API, указывать ожидаемые коды ответов, возможные ошибки и примеры использования.
- Не оставлять «мёртвый» код в виде закомментированных блоков; удалять его.

## Форматирование и структура
- Длина строки — не более 100 символов; длинные выражения разбивать с выравниванием.
- Функции должны быть компактными: не более 50 строк; если логика разрастается — выносить в отдельные функции.
- Избегать вложенных блоков глубже 3–4 уровней; при необходимости использовать ранние возвраты (`if (!ok) return error.Something;`) для упрощения структуры.

## Тесты и тестирование
- Все функции должны быть тестированы; тесты должны быть автоматическими.
- Тесты должны охватывать граничные условия и проверять все возможные ошибки.
- Тесты должны давать одинаковый результат при одинаковых входных данных.
- Тесты должны проверять в том числе и случаи, когда входные данные некорректны.
- Тесты должны проверять в том числе и случаи, когда выделение памяти невозможно с использованием `std.testing.FailingAllocator`.
- Название теста должно явно описывать сценарий и ожидаемый результат.
- В тестах используйте `defer` для освобождения аллокаторов, файлов и других ресурсов, чтобы избежать утечек памяти даже в тестах.

## Специфика консольного клиента Linux
- Обрабатывать сигналы (например, SIGINT) для корректного завершения: закрывать соединения.
- Логирование выполнять через отдельный модуль логов; избегать избыточных сообщений в stdout, если они мешают выводу CLI.
- Аргументы командной строки обрабатывать через библиотеку [args.zig](https://github.com/ktarasov/args.zig.git), выводя понятное сообщение об использовании при ошибках.
